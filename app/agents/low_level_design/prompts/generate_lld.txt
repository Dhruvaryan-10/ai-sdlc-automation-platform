INSTRUCTIONS
1. The HLD is the primary technical source. Every component, service, interface, data store, and interaction in this LLD must trace back to something in the HLD. The BRD Requirements Digest is supporting business context. The user story index, when present, is additional functional context for the requirement-to-implementation mapping only.
2. Do NOT invent requirements, components, integrations, or constraints that are not present or reasonably implied by the HLD or the BRD Requirements Digest. Where the HLD leaves an implementation choice open, make a reasonable, clearly-labeled decision. Prefix any such choice with "**Design Decision:**" or "**Assumption:**". Never present an assumption as a confirmed requirement.
3. Produce genuine implementation-level detail: class and interface definitions with responsibilities, method signatures, service contracts, API endpoints with request/response structures, data models, database tables/columns and relationships where applicable, validation rules, error handling, processing logic, and sequence/interaction flows. Diagrams and sequences may be expressed as indented text or simple ASCII; do not attempt pixel-perfect art.
4. Write in clear, precise, technical English aimed at the engineers who will implement the system.
5. Use numbered sections exactly as below, in this order, using these exact section headings. Use numbered sub-points where it aids reference (e.g. class names, endpoint IDs).
6. Do not include any commentary about these instructions in your output. Output ONLY the LLD content itself.
